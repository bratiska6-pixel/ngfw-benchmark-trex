# Универсальное руководство: Ручное тестирование любого межсетевого экрана (NGFW) с помощью TRex Studio

Данное руководство содержит универсальную пошаговую инструкцию по проведению нагрузочного тестирования **любого** межсетевого экрана (Ideco, Positive Technologies, UserGate, Check Point, Fortinet, Континент 4, ViPNet, Palo Alto Networks, pfSense/OPNsense) с помощью веб-панели управления **TRex Studio** в ручном режиме без необходимости писать скрипты.

---

## 1. Универсальные требования к настройке целевого МЭ (DUT)

Чтобы генератор трафика Cisco TRex в режиме ASTF мог прокачивать двусторонний трафик через любой межсетевой экран, на МЭ необходимо выполнить ровно **4 стандартных шага**:

```text
[ Cisco TRex ASTF ]                                [ Любой целевой МЭ (DUT) ]
  Port 0 (192.168.1.2)  ====== LAN: 192.168.1.1 ======>  [ Входной порт LAN ]
  (Клиенты 16.0.0.0/8)                                         |
                                                         [ Модули инспекции: ]
                                                         [ L4 Firewall / DPI ]
                                                         [ IPS / No-NAT      ]
                                                               |
  Port 1 (172.10.1.2)   <===== WAN: 172.10.1.1 =======   [ Выходной порт WAN ]
  (Серверы 48.0.0.0/8)
```

### Шаг 1. Сетевые интерфейсы (L3 Routed Mode)
Назначьте IP-адреса на интерфейсах МЭ, смотрящих в сторону портов TRex:
* **Интерфейс LAN (Вход от клиентов):** `192.168.1.1/24`
* **Интерфейс WAN (Выход к серверам):** `172.10.1.1/24`

### Шаг 2. Статическая маршрутизация
МЭ должен знать, куда отправлять трафик виртуальных сетей клиентов и серверов TRex:
* **Маршрут к клиентам:** Сеть `16.0.0.0/8` ➔ Next-Hop `192.168.1.2` (через интерфейс LAN).
* **Маршрут к серверам:** Сеть `48.0.0.0/8` ➔ Next-Hop `172.10.1.2` (через интерфейс WAN).

### Шаг 3. Отключение NAT (Правило No-NAT / Bypass NAT)
> [!IMPORTANT]
> **Критически важно:** По умолчанию большинство офисных МЭ автоматически включают маскарадинг (SNAT) для всего исходящего трафика. Если оставить NAT включенным:
> 1. TRex не сможет сопоставить ответы серверов с клиентскими сессиями.
> 2. Пул портов NAT (65 535) мгновенно переполнится при стресс-тесте.
* **Действие:** Создайте правило NAT-исключения: Трафик с источником `16.0.0.0/8` и назначением `48.0.0.0/8` ➔ **Не транслировать (No-NAT / Accept без трансляции)**.

### Шаг 4. Разрешающее правило межсетевого экрана (Firewall Policy)
* **Правило:** Зона LAN ➔ Зона WAN.
* **Источник:** `16.0.0.0/8` (или Any).
* **Назначение:** `48.0.0.0/8` (или Any).
* **Сервисы/Протоколы:** Any (или TCP/UDP/ICMP).
* **Действие:** `Allow` / `Pass`.

## 2. Пошаговая работа в веб-интерфейсе TRex Studio

Веб-панель TRex Studio позволяет наглядно управлять генерацией и видеть отклик целевого МЭ в виде интерактивных графиков.

### Шаг 1. Открытие веб-панели и авторизация
1. Откройте в браузере адрес вашего генератора TRex:
   `http://<IP_ГЕНЕРАТОРА>:8080/`
2. Авторизуйтесь под учетной записью администратора стенда.

### Шаг 2. Проверка связности и разрешение ARP
Перед запуском генерации TRex обязан разрешить MAC-адреса интерфейсов МЭ:
1. В верхнем блоке статуса найдите порты:
   * **Port 0:** `192.168.1.2` (Gateway: `192.168.1.1`)
   * **Port 1:** `172.10.1.2` (Gateway: `172.10.1.1`)
2. Нажмите кнопку **«Resolve ARP»**.
3. **Критерий успеха:** Индикаторы ARP возле обоих портов должны загореться зеленым цветом, а в полях появятся MAC-адреса сетевых интерфейсов тестируемого МЭ.
   *(Если ARP не разрешается: проверьте доступность IP шлюза, включение Promiscuous Mode на vSwitch и отсутствие блокировки ARP-запросов на МЭ).*

### Шаг 3. Запуск базового теста (Baseline Throughput)
1. В выпадающем списке профилей выберите: **`astf/http_simple.py`**.
2. Установите параметры:
   * **Multiplier (Множитель):** `50` или `100` (для плавного старта).
   * **Duration (Длительность):** `20` секунд.
3. Нажмите кнопку **«Start Traffic»**.
4. **Что наблюдать на графиках:**
   * **RX Throughput (зеленый график):** Скорость приема трафика на сервере. В норме должна быстро выйти на ровное плато.
   * **TX Throughput (синий график):** Скорость отправки запросов клиентами.
   * **CPS:** Частота открытия новых сессий.
   * **Drops / Errors:** Должны быть строго равны **0**.

### Шаг 4. Ступенчатый стресс-тест на предел производительности
Для определения предельной пропускной способности МЭ проводите серию коротких тестов с повышением множителя:
1. `Multiplier = 100` ➔ Фиксируем полосу (например, 400 Мбит/с).
2. `Multiplier = 200` ➔ Полоса растет (например, до 700 Мбит/с).
3. `Multiplier = 300` ➔ Смотрим, продолжает ли расти полоса или выходит на насыщение.
4. `Multiplier = 500+` ➔ Если начинаются потери пакетов (`drops > 0`) или задержки (`latency`) подскакивают в сотни раз — вы достигли физического предела процессора или таблицы соединений МЭ.

### Шаг 5. Тестирование реалистичного микса (Enterprise SFR)
1. Выберите профиль: **`astf/sfr.py`**.
2. Установите множитель: `Multiplier = 50` (профиль тяжелый, содержит HTTP, SMTP, DNS, IMAP).
3. Нажмите **«Start Traffic»**.
4. **Оценка результата:**
   * Проверьте показатель **CPS**: сколько сложных разнородных сессий в секунду успевает зарегистрировать МЭ.
   * Проверьте **RX Throughput**: какую непрерывную пропускную способность МЭ держит при передаче реального корпоративного трафика.

### Шаг 6. Тестирование сигнатур DPI и блокировки приложений
Если на тестируемом МЭ включен модуль глубокого анализа пакетов (DPI) и настроены правила запрета (например, блокировка Telegram, BitTorrent или YouTube):
1. Перейдите на вкладку **«DPI Traffic Builder»** в TRex Studio.
2. Сгенерируйте сессии с целевыми заголовками `SNI` (для TLS 1.2/1.3) или `Host` (для HTTP 80):
   * Пример: `telegram.org`, `youtube.com`.
3. Запустите трафик.
4. **Результат:**
   * Если правило DPI работает: трафик с данным SNI будет мгновенно сброшен (`0 байт` получено на сервере, в логах МЭ появится запись `Drop / Block`).
   * Эталонный трафик (например, `yandex.ru`) при этом должен проходить беспрепятственно.

## 3. Мониторинг целевого МЭ во время испытаний

Во время прогона теста обязательно откройте консоль или веб-интерфейс самого тестируемого МЭ:
1. **Загрузка CPU:** Смотрите распределение по ядрам. Если одно ядро загружено на 100% (мягкие прерывания `si / softirq`), а остальные простаивают — на МЭ не настроена многопоточная обработка (RSS/SMP affinity).
2. **Таблица соединений (`conntrack` / Sessions):** Наблюдайте за числом активных сессий. Значение не должно упираться в максимальный системный лимит `sysctl net.netfilter.nf_conntrack_max`.
3. **Ошибки интерфейсов:** Проверяйте счетчики `overruns` и `dropped` на сетевых адаптерах МЭ (`ip -s link show`).
