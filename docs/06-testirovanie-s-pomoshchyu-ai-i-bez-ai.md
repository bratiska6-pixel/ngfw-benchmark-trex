# Методология тестирования NGFW: С использованием ИИ (AI-Driven) и традиционным способом (Без ИИ)

Данный документ описывает два подхода к проведению нагрузочных испытаний межсетевых экранов нового поколения (NGFW) с использованием аппаратного/виртуального генератора трафика **Cisco TRex ASTF**:
1. **AI-Driven подход:** Полностью автоматизированное тестирование с помощью автономного ИИ-агента (LLM / Agentic AI).
2. **Классический подход (Без ИИ):** Ручное или полуавтоматическое тестирование сетевым инженером через веб-панель **TRex Studio** и консоль `trex-console`.

---

## 1. Сравнительная матрица подходов

| Параметр | AI-Driven подход (С ИИ-ассистентом) | Классический подход (Без ИИ) |
|---|---|---|
| **Время полного цикла тестирования 2-х NGFW** | **15–25 минут** (включая генерацию отчета) | **2–4 часа** рутинных ручных действий |
| **Переключение шлюзов и адаптация конфигов** | Автоматически скриптами «на лету» (3 сек) | Ручное редактирование YAML и рестарт служб |
| **Сбор посекундной телеметрии (CPS, Bw, Flows)** | Непрерывный программный экспорт в структурированный JSON | Визуальная фиксация пиков с экрана консоли |
| **Генерация презентационных отчетов** | Автоматическая сборка автономного HTML-отчета с Chart.js | Ручной перенос цифр в Excel и построение диаграмм |
| **Человеческий фактор / Ошибки** | Исключены случайные искажения параметров профилей | Возможны опечатки при внесении шлюзов или ARP |
| **Требования к квалификации инженера** | Достаточно уметь сформулировать задачу агенту | Глубокое знание ASTF API, Linux CLI и сетевого стека |

---

## 2. Подход №1: Как проводить тестирование с помощью ИИ (AI-Driven)

В данном сценарии ИИ-агент выступает в роли виртуального ведущего сетевого инженера по автоматизации (Network Automation Engineer).

```text
+-----------------------+      Запросы и команды      +-------------------------------+
|                       | -------------------------> |        Cisco TRex ASTF        |
|                       |                            |       (RPC API порт 4500)      |
|                       | <------------------------- +-------------------------------+
|                       |      Посекундный JSON      
|                       |                                
|                       |      Конфигурация/Статус    +-------------------------------+
|       AI АГЕНТ        | -------------------------> |       Тестируемые NGFW        |
|  (Agentic Assistant)  |                            |   (REST API / SSH / CLI)      |
|                       |                            +-------------------------------+
|                       |                                
|                       |      Сборка визуализации    +-------------------------------+
|                       | -------------------------> |   Интерактивный HTML-отчет    |
|                       |                            |   (Chart.js, KPI, Аналитика)  |
+-----------------------+                            +-------------------------------+
```

### Архитектура работы ИИ-агента:
1. **Анализ окружения и валидация паритета:**
   * ИИ опрашивает API гипервизора (ESXi / Proxmox / KVM) и проверяет, что тестируемые ВМ имеют равные вычислительные ресурсы (vCPU, RAM, типы виртуальных сетевых адаптеров).
   * Проверяет настройки Promiscuous Mode на виртуальных коммутаторах (vSwitch).
2. **Верификация сетевого стека:**
   * Проверяет доступность интерфейсов через SSH или REST API МЭ.
   * Убеждается в наличии статических маршрутов на сети генератора (`16.0.0.0/8` и `48.0.0.0/8`).
   * Контролирует отсутствие трансляции адресов (No-NAT).
3. **Автоматический запуск циклов нагрузки:**
   * ИИ запускает сценарий на Python, использующий `trex.astf.api.ASTFClient`.
   * Загружает профили `astf/http_simple.py` и `astf/sfr.py`.
   * Автоматически выполняет `resolve()` для прогрева ARP-кэша.
   * Запускает генерацию с заданными множителями (`mult=100`, `mult=300`, `mult=50`).
   * В реальном времени логирует метрики (CPS, RX Throughput, TX Throughput, Active Flows).
4. **Бесшовное переключение на второй шлюз:**
   * По завершении первого цикла ИИ модифицирует `/etc/trex_cfg.yaml`, перезапускает службу `trex-engine`, верифицирует новый ARP и прогоняет идентичный комплекс тестов для соперника.
5. **Генерация презентационных артефактов:**
   * ИИ автоматически агрегирует метрики в JSON и компилирует автономный HTML-отчет с интерактивными графиками, сравнительными таблицами, анализом TCO и архитектурными выводами.

### Пример промпта для постановки задачи ИИ:
```text
У меня развернут генератор Cisco TRex ASTF на сервере <TREX_IP> и два межсетевых экрана 
(NGFW-1 с IP 192.168.1.1/172.10.1.1 и NGFW-2 с IP 192.168.1.5/172.10.1.5).
Проведи сравнительное тестирование сетевой производительности обоих NGFW:
1. Проверь аппаратный паритет ресурсов на гипервизоре.
2. Прогони профили astf/http_simple.py (mult 100 и 300) и astf/sfr.py (mult 50).
3. Собери метрики CPS, Throughput RX/TX и потери пакетов.
4. Сформируй красивый HTML-отчет с графиками Chart.js для руководства.
```

## 3. Подход №2: Как проводить тестирование БЕЗ ИИ (Классический ручной путь)

Если в вашей инфраструктуре нет доступа к ИИ-агентам, любой сетевой инженер может провести полноценное тестирование вручную.

### Вариант А: Через веб-интерфейс TRex Studio (Самый наглядный)
1. **Подготовка МЭ:** Настройте L3 IP-адреса, статические маршруты на `16.0.0.0/8` и `48.0.0.0/8`, правило No-NAT и разрешающую политику Firewall.
2. **Вход в панель:** Откройте браузер по адресу `http://<TREX_IP>:8080/`.
3. **Разрешение ARP:** Нажмите кнопку **«Resolve ARP»** в строке портов. Убедитесь, что статус стал зеленым.
4. **Выбор профиля:** Выберите `astf/http_simple.py`, задайте множитель `mult=100`, длительность `20s` и нажмите **«Start Traffic»**.
5. **Наблюдение:** Наблюдайте за живыми графиками Throughput и CPS. Зафиксируйте максимальное плато.
6. **Стресс-тест:** Повторите тест с множителем `mult=300`.
7. **Тест корпоративного трафика:** Выберите профиль `astf/sfr.py`, задайте `mult=50` и зафиксируйте показатели CPS и скорости.
8. **Переключение на второй МЭ:**
   * Подключитесь по SSH к ноде TRex: `ssh user@<TREX_IP>`.
   * Отредактируйте `/etc/trex_cfg.yaml`, указав IP шлюзов второго МЭ.
   * Перезапустите службу: `sudo systemctl restart trex-engine`.
   * Вернитесь в веб-панель и повторите шаги 3–7 для второго устройства.

### Вариант Б: Через консоль TRex CLI (`trex-console`)
Для инженеров, предпочитающих работать исключительно через терминал:

```bash
# 1. Запуск консоли ASTF
cd /opt/trex/v3.08
./trex-console --astf

# 2. Проверка портов и ARP
astf> show
astf> resolve

# 3. Запуск профиля HTTP Baseline
astf> start -f astf/http_simple.py -m 100 -d 20

# 4. Открытие терминального дашборда мониторинга (TUI)
astf> tui
# Наблюдаем за показателями Tx/Rx Bps, Tx CPS, Active Flows. Для выхода из TUI нажать 'q'.

# 5. Запуск профиля Enterprise Mix (SFR)
astf> start -f astf/sfr.py -m 50 -d 30
astf> tui

# 6. Остановка трафика в случае нештатной ситуации
astf> stop
```

### Вариант В: С помощью готового Python-скрипта из этого репозитория
В репозитории подготовлен универсальный скрипт, автоматизирующий работу через TRex ASTF API:

```bash
# Запуск теста для целевого МЭ
python3 scripts/benchmark_astf.py \
    --server 127.0.0.1 \
    --profile astf/http_simple.py \
    --mult 100 \
    --duration 15 \
    --output result_http100.json
```

Скрипт автоматически подключится к демону TRex, разрешит ARP, выполнит прогон, выведет посекундный лог в терминал и сохранит структурированный JSON с метриками.
