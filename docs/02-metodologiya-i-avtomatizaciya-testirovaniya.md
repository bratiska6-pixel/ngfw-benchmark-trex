# Методология и автоматизация тестирования Cisco TRex ASTF

Данный документ описывает методику испытаний, профили генерации трафика, механизм динамического переключения шлюзов без перезагрузки стенда и скрипты автоматизации.

---

## 1. Режим генерации трафика: Cisco TRex ASTF

В отличие от режима STL (Stateless), в котором генерируются изолированные «сырые» пакеты без контроля состояния, для тестирования межсетевых экранов нового поколения (NGFW) используется **ASTF (Advanced Stateful Traffic Generator)**:
* Эмулируется полноценный стек TCP/UDP: трехстороннее рукопожатие (`SYN` ➔ `SYN-ACK` ➔ `ACK`), передача полезной нагрузки L7 (HTTP/TLS/DNS/Mail), корректное завершение соединений (`FIN` / `RST`).
* NGFW обязан распознавать каждое соединение, вести таблицу сессий (conntrack / flow table), выполнять инспекцию протокола L7 и пропускать трафик в обоих направлениях.

---

## 2. Профили нагрузки

Для тестирования были отобраны 3 ключевых отраслевых сценария:

### Сценарий 1: Базовый L7 HTTP-трафик (`http_simple.py`, mult=100)
* **Цель:** Оценка базовой пропускной способности при стандартном веб-трафике с умеренным темпом создания новых сессий.
* **Параметры:** Профиль `astf/http_simple.py`, множитель `mult=100`, длительность 12–15 секунд.

### Сценарий 2: Стресс-тест L7 HTTP с высоким CPS (`http_simple.py`, mult=300)
* **Цель:** Проверка поведения межсетевого экрана при утроенной частоте открытия/закрытия L7-сессий.
* **Параметры:** Множитель `mult=300`. Проверяет устойчивость таблиц сессий и процессора к пиковым нагрузкам.

### Сценарий 3: Смешанный корпоративный трафик Enterprise Mix (`sfr.py`, mult=50)
* **Цель:** Имитация реального рабочего дня предприятия с разнородным протокольным составом (SFR = Stateful Flow Records: HTTP, HTTPS, SMTP, IMAP, DNS, POP3).
* **Параметры:** Профиль `astf/sfr.py`, множитель `mult=50`. Тестирует способность ядра распределять потоки разного размера и сложности.

## 3. Механизм динамического переключения шлюзов

Поскольку обе ВМ (Ideco и PT NGFW) подключены к одним и тем же L2 порт-группам, одновременный пропуск трафика через обе машины невозможен из-за пересечения маршрутов. 

Для чистоты эксперимента стенд переключается на лету за 3 секунды:
1. В конфигурационном файле `/etc/trex_cfg.yaml` на ноде TRex переопределяются шлюзы:
   * **Для Ideco NGFW:**
     ```yaml
     - port_id: 0
       ip: 192.168.1.2
       default_gw: 192.168.1.1
     - port_id: 1
       ip: 172.10.1.2
       default_gw: 172.10.1.1
     ```
   * **Для PT NGFW:**
     ```yaml
     - port_id: 0
       ip: 192.168.1.2
       default_gw: 192.168.1.5
     - port_id: 1
       ip: 172.10.1.2
       default_gw: 172.10.1.5
     ```
2. Служба `trex-engine.service` перезапускается:
   ```bash
   sudo systemctl restart trex-engine
   ```
3. Выполняется принудительное разрешение ARP через Python ASTF API:
   ```python
   client.resolve()
   ```

## 4. Скрипт автоматического запуска тестирования

Скрипт `scripts/benchmark_local.py` написан с использованием официальной библиотеки `trex.astf.api.ASTFClient` и выполняет:
1. Подключение к демону TRex ASTF RPC (порт 4500).
2. Загрузку и компиляцию Python ASTF-профилей на лету.
3. Посекундный сбор телеметрии:
   * `cps` (Connections Per Second — соединений в секунду);
   * `rx_mbps` / `tx_mbps` (Пропускная способность на клиентском и серверном портах);
   * `active_flows` (Число одновременных активных сессий);
   * `queue_drops`, `tcp_retransmissions` (Потери и повторные передачи).
4. Экспорт сырых результатов в структурированный JSON: `benchmark_results.json`.

Исходный код скрипта доступен в каталоге: [scripts/benchmark_local.py](scripts/benchmark_local.py).
